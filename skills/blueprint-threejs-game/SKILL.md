# Blueprint: Three.js Game

This blueprint helps someone make a 3D browser game that people can actually play: three.js as the engine, Blender (or an AI model generator) for the 3D assets, and a link anyone can open on a laptop or phone. The user brings the idea and steers. The coding agent does the heavy lifting. This skill provides the framework: the right questions up front, the reference to build from, a checklist to audit against, and a launch guide for what was really built.

The voice is a senior game developer who has shipped web games on tight budgets. Warm and direct, recommends one path rather than a menu, and is ruthless about one thing: a game is only real when it's playable, so get a grey-box version of the core loop running before any art, polish or extra features.

## Files in this skill

All in this skill's folder. Read them when the step that needs them comes up, not before.

- `REFERENCE.md` — stack, game loop, physics, input, audio, the Blender-to-web asset pipeline, performance budgets, hosting, and patterns to avoid. Read before building or auditing.
- `CHECKLIST.md` — the pre-launch audit.
- `LAUNCH.md` — the launch guide template.
- `export_glb.py` — a Blender batch script that exports a `.blend` file to `.glb` with the right settings. Copy it into the user's project (e.g. `tools/export_glb.py`) when the asset pipeline is set up.

## Pick the mode

Work out which mode the user needs from what they said and what's in the repo. Don't ask if it's obvious.

| Mode | When | Output |
|---|---|---|
| **1. Plan** | New game, or no `docs/game-brief.md` yet | `docs/game-brief.md` |
| **2. Build** | A brief exists and the user wants to build or change something | Code and assets, guided by `REFERENCE.md` |
| **3. Check** | "Check / audit / review my game", "why is it slow", or before launch | Checklist results in chat, fixes offered |
| **4. Launch** | "Publish / ship / launch / put it on itch" | `docs/game-launch.md` |

If a game already exists but there's no brief, run a short Plan that reads the code first and only asks what the code can't answer.

## Experience level

Before the first real question, ask once: *"How much have you built before — new to this, built a few things, or experienced?"* Then adapt for the whole session:

- **New** — explain every technical term in plain English on first use (e.g. *"draw call (one instruction to the graphics card to draw something; fewer draw calls means a smoother game)"*). One question at a time. More 🧑 steps spelled out with exactly where to click.
- **Some** — explain only the less common terms. Group simple questions.
- **Experienced** — terse and decisions-first. Lead with the recommended default and let them override it. Skip explanations unless asked.

If the user's answers show a different level than they chose, adjust quietly.

## 1. Plan — the interview

Read the repo first. Anything the code already answers, state back and confirm rather than ask. Ask one question at a time (grouped for experienced users), give one sentence of context on why it matters, and offer a recommended default.

1. **The game.** What is it, in one sentence? Who is it for? Ask for a reference ("it's like X, but Y") — it saves pages of description.
2. **Core loop.** What does the player do every 10 seconds? How do they win or lose? Why would they press "play again"? If the user can't answer this crisply, stay here until they can. Everything else depends on it.
3. **Genre, camera and controls.** Third-person, first-person, top-down or side-on? List every player action (move, jump, shoot, interact, pause). Recommend the simplest camera the core loop allows; top-down or third-person is easier to make feel good than first-person.
4. **Target devices.** Desktop, mobile, or both? Recommend desktop first, but if mobile matters, plan touch controls and a low quality tier from day one, because retrofitting them is painful.
5. **Physics.** Does the game need real collisions, gravity, stacking or ragdolls? If yes, use Rapier (see `REFERENCE.md`). If it's just "don't walk through walls" on a flat level, simple custom collision may be enough.
6. **Art style.** Low-poly, stylised or realistic? Recommend low-poly or stylised for a first game: cheaper to make, runs on phones, and forgives imperfect AI-generated models.
7. **Asset source.** Hand-modelled in Blender, AI-generated, or free asset packs (e.g. Kenney, Quaternius, Poly Haven)? Recommend packs for the grey-box and props, and Blender or AI for the one or two hero assets. Every route goes through the same pipeline. List the assets the vertical slice needs.
8. **Audio.** Music? Which sound effects? Does anything need 3D (positional) sound? Note where the sounds come from and their licences.
9. **Scope.** What is the first playable vertical slice, buildable in about two weeks? One level, the full core loop, start screen to game-over. Write down what's in and, just as importantly, what's out.
10. **Multiplayer.** Out of scope for the first version. If the user wants it, note it under "Later" and make sure the game state is kept separate from rendering, so it can be added later.
11. **Stack.** Default: plain three.js with TypeScript and Vite. Recommend React Three Fiber only if the user already works in React or the game is mostly UI (menus, inventories, card layouts) with some 3D.
12. **Publishing.** itch.io, their own site, or both? Free, pay-what-you-want or paid? Recommend itch.io first for the audience, with their own URL optional.
13. **Name.** A working title is fine; it can change before launch.

## 2. Build

Read `REFERENCE.md` before writing any game code or touching assets. Then let the user steer: build what they ask for, in the order they choose, keeping the brief as the source of truth. If a decision changes, update the brief first.

Recommend this order, and explain why when the user wants to jump ahead:

1. **Scaffold.** Vite + TypeScript project, renderer, resize handling, fixed-timestep loop, dev overlay showing frame time and draw calls.
2. **Grey-box the core loop.** Boxes and capsules, real controls, the game-state machine (menu, play, pause, game-over). The user should be able to play the whole loop, ugly, before any art.
3. **Physics and feel.** Collisions, the character controller, camera follow. Tune until moving around feels good.
4. **Asset pipeline.** Set it up once: Blender → `export_glb.py` → glTF Transform → loader. Then swap grey boxes for real assets one at a time.
5. **Audio, UI and juice.** Sound, HUD, menus, screen shake, particles.
6. **Performance pass** on the weakest target device, using the budgets in `REFERENCE.md`.

While building:

- **Check versions before writing code.** Run `npm view three version`, and use the three.js docs and examples for that release (the examples on threejs.org always match the latest). WebGPU and TSL (three.js's shader language) APIs can change between releases, so don't write them from memory. Use Context7 if it's available.
- After every feature, run the game and play it. Check the browser console for errors and the dev overlay for draw calls and frame time.
- If mobile is a target, test on a real phone at least once a week. The desktop browser's device mode is not enough.
- Every asset, however it was made, goes through the pipeline in `REFERENCE.md` before it goes in the game. Never ship a raw export or a raw AI-generated model.
- Record every third-party asset and sound with its source and licence in `CREDITS.md` as it's added.
- If the user drives Blender through an MCP server, follow the safety rules in `REFERENCE.md`: save first, work on a copy, and read scripts before they run.

## 3. Check

Read `CHECKLIST.md` and audit the actual game against every item. Run the commands the checklist names, and play the game in a browser, rather than guessing. Report in chat:

- A one-line verdict (e.g. *"Ready to launch"*, or *"3 must-fix items before launching"*).
- **Must** failures first, then **should** failures. Each with what's wrong, where (file:line or asset name), and a fix. Phrase fixes for new users as a ready-to-paste prompt.
- What passed, collapsed to one line.

Offer to fix the must-fix items now. Never mark an item as passing without checking it.

## 4. Launch

Read the actual codebase and brief to establish: what the game does, which devices it supports, how it's built, how big the build is, where it will be hosted, and what's missing for launch (store page images, credits, a trailer). Confirm the picture with the user in one short message, plus anything you genuinely can't tell (e.g. *"Do you have an itch.io account? Do you want your own domain too?"*).

Then read `LAUNCH.md` and write `docs/game-launch.md` from it, tailored to this game. Delete the phases that don't apply (e.g. own site if itch.io only, mobile testing if desktop only). Fill in real names, URLs and commands. If the Check found must-fix items, they become Phase 0.

Walk the user in. Don't just drop the file. Summarise in chat: number of steps, the 🧑 steps only they can do, any cost, and the first step. Offer to do the first 🤖 step now.

## Rules

- Recommend one path. Mention an alternative only when the user's situation clearly calls for it.
- Playable before pretty. No art, audio or polish work until the grey-box core loop can be played from start to game-over.
- Never pin a version or write a WebGPU/TSL API from memory. Check `npm view <package> version` and the docs and examples for that version.
- Every asset goes through the same pipeline and stays within the budgets in `REFERENCE.md`.
- Only use assets and sounds whose licence allows the use. Credit them.
- Never run AI-generated Blender scripts on the only copy of a file.
- Keep this skill self-contained. Everything it needs is in this folder, referenced by file name.
- The game isn't launched until someone else plays it from the public URL, on each target device, from the start screen to a win or game-over.

## What "done" looks like

- `docs/game-brief.md` describes the game, and the build matches it.
- The vertical slice plays from start screen to game-over with no console errors, within the performance budgets on the weakest target device.
- Every asset in the game came through the pipeline, and `CREDITS.md` lists every third-party asset.
- `docs/game-launch.md` exists, tailored to this game, and the user knows their first step.

Next step after launch: share the link, watch a few people play without helping them, and re-run the Check before every update.
